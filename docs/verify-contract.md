# 出处核查帮手共用的规矩（不要改这个文件）

## 为什么要核查

这本「GEO 实战手册」写给同时做很多产品的独立开发者。它的卖点是：每条结论后面都有出处和证据等级。读者点开出处，看到的内容必须能撑住那句话。抽查 75 句时，有 11% 的句子话说得比出处宽，比如漏了平台范围、把发布日期写成现状、引错了出处。你要把自己负责的页面里每一句带出处的话都核一遍，有问题当场改。

## 你手上的东西

- 你的工作副本（任务里写了路径和分支），只改任务里列出的页面。
- 运行 `node scripts/extract-claims.mjs > /tmp/<你的分支名>-claims.tsv`，能拿到全站每一句带出处的话，第一列是页面。只看你负责的页面。
- 出处 id 的格式是「调研稿编号-s 编号」。`02-s21` 指 `research/02-*.md` 末尾出处表里的 S21。编号 08 及以上是小的补充稿，比如 `research/15-mentions-extra.md`。
- 几份稿子引用同一个链接时，id 会被并到第一次出现的那条。所以页面上写的 id 和表里显示的可能不同，指向的是同一个网址。核查时，同一网址在各份稿子里的记录都可以用。

## 每一句怎么核

1. 打开出处所在的调研稿，读出处表那一行，再在正文里搜它的标记（比如 `[S21]`），读上下文。
2. 调研稿还定不了，而且出处是 A 或 B 级，可以用 WebFetch 打开原文看一次。
3. 判断：
   - **SUPPORTED**：出处说了这件事。
   - **PARTIAL**：大意对，但数字、日期、范围、归属不对或说过头了。
   - **UNSUPPORTED**：出处没说，或者说的是反的。
   - **CANNOT_CHECK**：写明原因。
4. PARTIAL 和 UNSUPPORTED 当场改页面：
   - 能改准就改句子，让它和出处一致。
   - 别的调研稿里有能撑住它的出处，就换 id。
   - 都不行，就删掉这句，或者改成「还没查清」。
   - 改完的句子要守 `MAINTAINING.md` 的「说人话」规矩：短句，一句一个意思，不用长破折号。
5. 别动没问题的句子，也别顺手改写文风。

## 记下来

在 `docs/verify-<分支名的最后一段>.tsv` 写一张表，列：page、claim、ids、verdict、evidence（在哪找到的：文件和行号，或打开的网址）、change（改成了什么，没改就空着）。每格一行，格子里不要有 tab。只记 PARTIAL、UNSUPPORTED、CANNOT_CHECK 的行，再在最后一行写各结论的总数。

## 做完怎么检查

1. 在你的工作副本里跑 `npm run build`，没有 `✗`。
2. `git diff --stat` 里只有你负责的页面和你的 tsv。
3. 用明确路径提交，提交信息写「核查了哪几页，改了几句」。

不要启动开发服务器，只用 `npm run build`。`/Volumes/T7-usb/orca/`、`.shared-node-modules`、`OpenHands` 下的进程不是你的，别动。

## 返回报告

只写：分支和提交 SHA；各结论的数量；每条改动一行（页面、原句前 20 字、问题、怎么改的）；构建最后一行。
