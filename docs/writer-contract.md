# 写作帮手共用的规矩（不要改这个文件）

## 这本书是给谁、做什么的

用户是一位独立开发者，一个人做很多产品：Chrome 插件、用 Astro 搭在 Cloudflare 上的静态教程站、会员网站、微信小程序、开源 GitHub 仓库、提示词和 Skill 合集，同时面向中文和全球用户。

这个网站叫「GEO 实战手册」，副标题「让 AI 在回答里推荐你的产品」。读者和用户一样：会写代码，但不是 SEO 专家。读完一页，读者要能拿自己的产品照着做，知道做完怎么检查有没有生效，也知道哪些活能交给 AI 做。

这本书和网上大多数 GEO 文章的区别：**每条建议都标着出处和证据强度**。有实证的做法和没人验证过的说法分开写。宁可写「这一点还没有可靠数据」，也不写没有出处的结论。

## 开工前先读

1. `MAINTAINING.md`：写作规矩（「说人话」那一节必须照做）、组件怎么用、MDX 的坑。
2. `docs/research-contract.md`：证据等级 A/B/C/D/X 的意思。
3. 你的任务里点名的调研稿，**全文读完**，不要只看总结。
4. 你要改的页面现在的样子（多数是「正文编写中。」占位）。

## 引用出处

- 每个事实性的说法后面，紧跟 `<Src ids="02-S1 03-S5" />`。id 是「调研稿编号-S 编号」，从调研稿末尾的出处表里抄。大小写都行。几份稿子重复的同一个链接，用哪个编号都能解析。
- 只引用调研稿出处表里有的条目。需要新出处时：用 WebFetch 打开原文核实，然后在你自己的补充稿 `research/<你的编号>-extra.md` 里加一行（表头和调研稿一样），再跑 `node scripts/import-sources.mjs`。补充稿你负责提交；生成的 `src/data/sources.gen.js` 不要提交（提交前 `git checkout src/data/sources.gen.js`），主对话合并后会统一重新生成。
- 措辞跟着证据走：
  - A、B：直接说。B 级写出样本量，比如「Ahrefs 统计了 7.5 万个品牌」。
  - C：写成「一次实测发现」「一家代理公司的数据显示」。
  - D：只能写成「有人主张……，没有数据支持」，或者干脆不写。
  - X：只在讲「过时的说法」时出现。
  - 发布方卖 GEO 工具的（出处表标了利益相关），提一句「这是卖工具的公司自己的数据」。
- 调研稿之间说法矛盾时，两边都写，说清楚谁说了什么，再给读者一个能自己验证的办法。
- 会变的东西（爬虫名、后台菜单、价格、默认设置）后面写「（截至 2026-11）」。

## 每页怎么写

- frontmatter：`tldr`（不超过 40 字，说读者做完能得到什么）、`description`（一句话，给搜索结果用）。How-to 再加 `time`（大概要多久）和 `for`（适合什么产品）。`step` 已经写好，不要改。
- **先做，后讲。** 每节先给能照抄的东西（命令、配置、代码、提示词），再用一两句说为什么。
- 能复制的提示词和命令用 `Copy` 组件。做完一步写「你应该看到」，用 `<Callout type="ok">`。容易做错的坑用 `<Callout type="warn">`。
- 每篇实操页都有一节「交给 AI 做」：给一段能直接发给 Claude Code / ChatGPT 的中文提示词，说清楚它做完你要检查什么。
- 页尾放「卡住了？」，用 `Q` 组件，按读者会看到的现象写问题。
- 例子用用户这类产品：Chrome 插件、Astro 教程站、会员站、小程序、GitHub 仓库。域名之类的写成 `` `<你的域名>` ``。
- 篇幅：完整教程每一步 1500 到 3000 字，How-to 每篇 1000 到 2500 字。宁可短而准。
- 站内链接只链 `src/data/nav.js` 里有的页面（`/guide/<slug>/`、`/howto/<slug>/`、`/start/<slug>/`、`/evidence/`、`/platforms/<slug>/`、`/tools/`、`/prompts/`、`/wiki/<slug>/`、`/faq/`、`/sources/`）。平台和 Wiki 的 slug 可能还没写好，链之前先看对应数据文件；没有的就不链。
- 标题、正文都用中文；产品名、爬虫名、配置字段、代码保持英文。
- 「说人话」规矩里的词表要照做：不写「赋能、抓手、闭环、落地」，不用「不是……而是……」，一句不超过 30 个字，表格不超过 3 列 5 行。不要用长破折号「——」。

## 只改你负责的文件

任务里写明了你负责哪些文件。别的文件一律不动，包括 `nav.js` 和 `figs.js`（这一轮不加 `Fig` 图示，想加图就写进返回报告）。你发现别人负责的文件该改，写进返回报告里。

## 你在自己的工作副本里干活

任务里写了你的目录（一个 git worktree，有自己的分支）。所有命令都在这个目录里跑。

## 做完怎么检查

1. 在你的目录里跑 `npm run build`。输出里没有 `✗`，最后一行是「内容检查」通过。
2. `grep -l "正文编写中" <你负责的页面>` 没有输出。
3. 把你写的每一页从头读一遍，按「说人话」规矩改一遍。
4. 用明确的路径提交（不要 `git add -A`），提交信息用一句平实的话说这次写了什么。

不要启动开发服务器（`npm run dev`、`astro preview`、`wrangler dev`）。只用 `npm run build`。如果确实启动了任何本地进程，返回前自己关掉，用 `pgrep -fl 'wrangler|workerd|esbuild|vite|astro'` 确认。`/Volumes/T7-usb/orca/` 下面的进程不是你的，别动。

## 返回报告

只写这些：分支名和提交 SHA；每页的字数（`wc -m`）；构建输出最后 3 行；你想写但找不到出处、所以没写的说法；你建议别人负责的文件加的内容（比如证据表里该有的做法、Wiki 该收的词）。不要把正文贴回来。
